## Что это

Веб-инструмент учёта денег вместо Финолога (подписка до ~21.11.2026). Один файл `index.html` без сборщика. Данные хранятся локально в браузере (IndexedDB; если недоступен, localStorage: на iPhone там около 5 МБ на сайт, этого не хватало для рабочей и тестовой баз вместе), при подключённом Firebase синхронизируются с Firestore. Рабочая база включена (`allowProd: true`), тестовая раздельная и нужна для проверок.

## Модель данных

- Запись: `id`, `kind` (expense, income, transfer_out, transfer_in), `wallet` (alfa, cash, promos, credit), `amount` в копейках со знаком, `date`, `planned`, `counterparty`, `article`, `project`, `description`, `bankState` (none, unconfirmed, confirmed, absent; старое `pending` читается как `unconfirmed`), `bankKey`, `pairId` (текст «пары не найдено» не считается парой), `source`, `extId` (номер строки сводной), `dateFixed`, `deleted` (мягкое удаление), `updatedAt`.
- Справочник статей: `id`, `name`, `kind`, `activity` (operating, investing, financing, none), `fixed`, `archived`, `system`, `updatedAt`. Статья в записи хранится названием.
- Проекты: `meta.projects[название] = { status: 'done'|'work', doneAt, result: { income, variable, fixedAllocated, net, … }, stage (5–19; 18 «Сдано», 19 «Рекламации»), f: { поля карточки CRM }, hist: [{ at, t }], lead: { снимок лида }, updatedAt }`. Результат закрытого проекта сохраняется снимком в момент закрытия; закрытие и возврат в работу сохраняют поля CRM. Проект без `stage` считается стоящим на стадии 5, закрытый на 18.
- Лиды: `meta.leads[id] = { id, name, status: 'lead'|'later'|'lost'|'won', stage (1–4), later (0–3), reason, projectKey, f: { поля лида }, hist, createdAt, updatedAt }`. Слияние по времени последней правки каждого лида, в облаке лежат в документе `state` вместе с проектами.
- Задачи: `meta.tasks[id] = { id, title, desc, zone (none|shop|office|director), ownerType ('project'|'lead'|''), ownerKey (название проекта или id лида), due (срок, дата), remind (напоминание, локальная дата-время YYYY-MM-DDTHH:mm), comment, status ('open'|'done'), doneAt (фактическая дата закрытия, ставится сама), hist, createdAt, updatedAt }`. Слияние по времени последней правки, в облаке лежат в документе `state`. Копия JSON версии 3 включает `meta.tasks`; копии версий 1 и 2 читаются.
- Облако Firestore: коллекция `money_<test|prod>_records` (документ на запись) и `money_<test|prod>_meta` с документами `state` (справочник, проекты), `decisions`, `log`, `settings` (ссылка скрипта выписок со временем изменения и список прочитанных файлов). Слияние по времени последней правки.
- Правила доступа: `firestore.rules`, список адресов с полными правами.
- Копия JSON: `version` 3 (CRM и лиды лежат в `meta.projects` и `meta.leads`, задачи в `meta.tasks`); копии версий 1 и 2 читаются, более новые отклоняются.

## Ключевые правила поведения

- Остаток кошелька включает все неподтверждённые выпиской записи (статус «Не подтверждено выпиской»), понятия «в пути» нет. Промос считается по учёту Дмитрия. Кредитный счёт личных средств вне общего итога.
- Перевод создаёт две парные записи, обе видны в журнале. Переводы и записи со статьёй «Корректировка остатка» не входят в отчёты и оборот, в остатки входят.
- Сверка выписки: кошелёк, сумма, дата ±4 дня для неподтверждённых записей; точная дата и сумма для уже подтверждённых без ключа выписки (привязка без дубля); дневная комиссия одной строкой привязывается к группе комиссий по платежам (сумма группы равна строке).
- Загрузка выписки (кнопка «Синхронизировать выписки» и ручная) сначала показывает окно с цифрами (строк, привязать, добавить новых с суммой, дубли, решения) и вносит данные только после подтверждения Дмитрия.
- Кнопка читает одну папку на Диске через скрипт Apps Script; банк по названию файла («Промос» значит Промос, «Выписка…» значит Альфа); файл должен заканчиваться на `.xlsx` или `.xls` (Диск при копировании добавляет «Копия (…)», такой файл нужно переименовать). Для iPhone ответ грузится скриптом-вставкой (JSONP).
- Принцип интерфейса (решение Дмитрия 02.11.2026): на лице только рабочие инструменты (Операции, Проекты, Лиды, дальше, возможно, база знаний), служебные функции и кнопки переезжают в «Настройки». «Выписки» (кнопка синхронизации, ручная загрузка, решения по сверке, переводы без пары) теперь третья вкладка настроек. Если есть нерешённые вопросы по выпискам, на кнопке «Настройки» и на вкладке «Выписки» показывается число.
- Режим администратора (ползунок «Админ» в шапке «Настроек», справа от заголовка, рядом со сменой темы; по умолчанию выключен, сбрасывается при перезапуске; когда включён, под шапкой короткая подсказка) показывает служебное: импорт сводной, исправление дат, восстановление из копии, сброс и тестовые данные, переключатель базы, ссылку скрипта, «Проверить связь», «Прогнать тестовую выписку».
- «Сбросить тестовую базу» чистит устройство и облако тестовой базы; сбрасывать нужно на каждом устройстве.
- Финансовый анализ на экране «Проекты» считается только по закрытым проектам, период по дате закрытия, результат из снимка при закрытии; блок свёрнут по умолчанию. Список проектов ниже за всё время.
- Список статей и журнал изменений в «Настройках» свёрнуты по умолчанию.
- CRM, проекты: вкладка «Проекты» показывает канбан (4 группы, 15 стадий от «Договор и предоплата» до «Рекламации») или список. Прежние проекты стоят на стадии 5. Переход вперёд требует обязательных полей (`KC.CRM.REQUIRED`: из стадий 5–9, 13, 15), назад без проверки. «Перенести без проверки полей» для прежних проектов пишется в историю. Мышью карточки перетаскиваются на компьютере (`DESK`), на телефоне кнопки в карточке. Решения Дмитрия 02.11.2026 (доделки): а) «Рекламации» отдельная стадия 19 после «Сдано»; б) переход в «Сдано» автоматически закрывает проект в «Деньгах» (период от первого до последнего поступления проекта, в долю входят поступления с проектом, постоянные расходы по статьям, как «Использовать эти сроки» при ручном закрытии); если поступлений нет, проект остаётся открытым на стадии «Сдано» и просит закрыть вручную; в обоих случаях есть «Отменить»; в) закрытые проекты лежат в колонке «Сдано» (последние 8, остальные по кнопке) и никогда не удаляются; перенос закрытого проекта на другую стадию (например, в «Рекламации») возвращает его в работу (итог пересчитается при следующем закрытии, в финансовый анализ он до тех пор не входит); г) дата сдачи считается сама: «Начало изготовления» плюс «Срок изготовления» в рабочих днях (пн–пт, праздники не учитываются), поле «Дата сдачи» тогда только для чтения, а без срока вводится руками; «Срок изготовления», «Начало изготовления» и «Дата заключения договора» вводятся руками; д) обязательные поля на остальных переходах (из 10–12, 14, 16, 17, 18, 19) остаются не определены; е) ответственный остаётся текстом, роли по стадиям отложены; ж) карточки никогда не удаляются.
- Единая карточка проекта (принцип Дмитрия): у проекта одна карточка на всю систему. Операция с проектом без карточки создаёт карточку на стадии 5 (`commit`, метка в истории «Карточка создана из операции»); подсказки «Проекта» в форме операции берут названия и из операций, и из карточек CRM (в том числе без операций); название, написанное иначе (регистр, пробелы, знаки, ё/е), записывается как в существующей карточке (`KC.findProjectName`). Дальше к той же карточке привязываются задачи и календарь.
- CRM, лиды: вкладка «Лиды» (воронка из 4 стадий, «Долгострой», «Не прошли» с причиной). Обязательные поля `KC.LEADS.REQUIRED`. «Договор заключён: создать проект» делает проект на стадии 5 с клиентом, телефоном, адресом, датой контакта, историей и снимком лида; название проекта не должно совпадать с карточкой проекта, лид получает статус `won`.
- CRM, задачи (решения Дмитрия 03.11.2026): новая вкладка «Задачи» между «Лиды» и «Настройки»; пять зон ответственности: «Не распределены», «Цех», «Офис», «Директор», «Подрядчики» (последняя добавлена 03.11.2026 по решению Дмитрия: она есть в дашборде заказов); задача без зоны попадает в «Не распределены». Поля задачи: название, описание, зона, карточка, срок завершения (дата, по ней сортировка и отметка «просрочена»), напоминание-будильник (дата и время), комментарий; фактическая дата закрытия записывается сама при «Выполнена». Будильник: когда время напоминания наступило, а задача не выполнена, на задаче появляется значок будильника (в списке задач, в блоке «Задачи» карточки проекта и лида, в самой задаче); экран обновляется раз в 30 секунд, если не открыта форма и нет ввода; оповещений вне экрана пока нет. Блок «Задачи» есть в карточках проектов и лидов с кнопкой «+ Задача» (карточка подставляется сама); вкладка «Задачи» оформлена канбаном, как «Лиды» и «Проекты» (решение Дмитрия 03.11.2026): пять колонок-зон; выполненные задачи с доски уходят и остаются в блоке «Задачи» карточки проекта или лида с пометой «выполнена», а также в виде «Выполненные». Виды: «Доска» (по умолчанию), «Список» (с фильтром по зоне), «Выполненные». Перенос в другую зону: мышью на компьютере (пишется в историю задачи), на телефоне выбором зоны в самой задаче. Есть поиск. По умолчанию (не подтверждено Дмитрием): задача может быть без карточки; удаления задач нет, только «Выполнена» и возврат в работу; карточка задачи меняется выбором в самой задаче.
- Перенос из дашборда заказов (разовый, решение Дмитрия 03.11.2026; после переезда дашборд закрывается): в режиме «Админ», «Данные и копии», кнопка «Выбрать файл дашборда (JSON)». Файл это выгрузка коллекции `projects` дашборда (репозиторий `doska-projects`, Firestore проекта `doska-projects`; выгрузку делает Claude, файл с названиями клиентов в репозиторий не кладётся). Окно сверки показывает цифры и ничего не вносит до «Внести». Стадии дашборда 1–11 становятся 5–15, 12 «Сдано» становится 18 (проект остаётся открытым, закрывать вручную), зоны задач: unassigned→«Не распределены», workshop→«Цех», office→«Офис», contractors→«Подрядчики». Название сверяется с карточками и проектами из операций без учёта регистра, пробелов, знаков и ё/е; «похожие» (общее слово от 6 букв) предлагаются выбором «склеить / создать новую». Повтор названия внутри файла получает «(2)». Карточка помечается `dashId` (id проекта в дашборде): повторный перенос находит её по метке, не создаёт дублей карточек и задач (id задачи `dash-<проект>-<задача>`) и не трогает стадию и поля, выставленные Дмитрием. Для уже существующих карточек пустые поля заполняются, заполненные остаются. У выполненных задач даты закрытия нет (в дашборде её не было). Цвет и порядок карточек не переносятся.
- Стадии «Склад» нет (решение Дмитрия 02.11.2026). Названия стадий и обязательные поля это черновик, ждут правки Дмитрия.
- Статьи в формах только выбираются из справочника, менять их можно только в Настройках. Enter в поле «Описание» сохраняет запись.
- Даты из xlsx: библиотека в поясе Москвы отдаёт полночь как 23:59:43 предыдущего дня; к дате прибавляется 10 минут (исправлено 02.11.2026). Кнопка «Исправить даты импорта» нужна только для данных, загруженных до исправления; в рабочей базе уже применена.

## Принцип хранения и копий (Дмитрий, 02.11.2026)

Система живёт в трёх независимых местах, потеря или взлом любого одного не должна терять систему:

1. **Механизм: сам инструмент.** Один файл `index.html` на GitHub Pages (репозиторий `sidorovdmtr/Sec`), в нём практически нет данных: только код и подключение к базе. Данные HTML берёт из базы, пустая оболочка должна оставаться такой.
2. **Данные: база.** Рабочая база в Firebase Firestore (проект `kubcrafter-finance`): доступ только через вход Google и правила `firestore.rules`; Google шифрует данные при хранении и передаче. Ключ в `config.js` не защита, он публичный по замыслу.
3. **Копии.** Периодические резервные копии данных (JSON для восстановления, xlsx для просмотра) на Google Диске: сначала вручную Дмитрием, позже автоматически по расписанию. Отдельно копия самого инструмента (файлы репозитория: `index.html`, `config.js`, `sw.js`, `manifest.webmanifest`, иконка, правила Firestore) на Диске, возможно по отдельному расписанию.

Что это даёт: сломали GitHub, инструмент разворачивается заново из копии (шаги в README); испортили или потеряли базу, данные восстанавливаются из последней копии (кнопка восстановления в режиме администратора); потерян доступ к обоим, всё разворачивается из третьего источника.

Сделано: кнопки копий JSON и xlsx, восстановление из JSON (формат версии 2 включает проекты, поля CRM и лиды; копии версии 1 читаются). Рабочая база на версии с CRM включена Дмитрием 02.11.2026: цифры не изменились, 62 проекта стоят на первой стадии «Договор и предоплата» и ждут раскладки.

Копия кода на Диск: скрипт `apps-script/code_backup.gs` написан и проверен на заглушках (решение Дмитрия 06.11.2026: папка по умолчанию, 8 копий, расписание раз в неделю); на живом Диске ещё не запускался, пока Дмитрий не вставит его в Apps Script и не выполнит `backupCode` и `setupTrigger`.

Не сделано: автоматические копии данных по расписанию (нужен планировщик; скрипт кода данные не копирует), проверка полного восстановления «с нуля» на чистой среде, одна инструкция развёртывания с нуля, Excel-копия полей CRM.

Безопасность хранения в Firebase выделена Дмитрием отдельным блоком: к нему вернуться в конце, когда система будет готова (правила доступа обоих проектов в консоли не проверены, ролей доступа нет).
